# 使用情境：醫療院所與法律事務所

本文件以醫療與法律事務所常見的文書處理、統計分析與系統操作為例，說明任務如何套用在 Privacy Agent + Operator 架構上。

- 架構決策以 [`docs/spec/`](spec/README.md) 為準，流程圖的元件定義見 [DESIGN.md](DESIGN.md)。
- 範例中的人名、病歷號、案號、金額皆為虛構。
- 除非特別註明，隱私等級一律為預設的「平衡」（ADR-0016）。

> 本架構的目的是降低敏感資料暴露給雲端 LLM 的範圍，並留下可稽核的紀錄。它不等同於符合個資法、醫療法、律師倫理規範或 HIPAA 等法規；實際導入仍需各機構依自身規範評估。

## 0. 閱讀方式

每個情境依序列出：

- **輸入**：使用者給了什麼。
- **偵測與政策**：命中的類別與「平衡」下的處理動作（ADR-0016）。
- **Route**：R0 直通、R1 最小化 + 別名化、R2 compute-to-data、R3 純本地、R4 詢問使用者（ADR-0005）。
- **雲端看到什麼**：送往 `trustZone = cloud` 的實際內容。
- **使用者確認點**：會打斷使用者的時機。
- **SLM／LLM 模式差異**。

「平衡」預設下與本文相關的類別動作：

| 類別 | 動作 |
|---|---|
| `health` 病歷、診斷、用藥 | confirm（別名化，本 Task 第一次外送前確認） |
| `gov_id` 身分證、健保卡、護照 | confirm |
| `financial_account` 帳號、卡號 | confirm |
| `org_confidential` 內部機密、未公開案情 | confirm |
| `person`、`contact`、`location` | alias |
| `dataset` 結構化或大量資料 | schema_only |
| `credential` | block（不可覆寫） |

建議醫療院所與律師事務所採用「嚴格」等級，或至少把 `person` 覆寫為 `confirm`。以下情境都會註明「嚴格」下的差異。

## 一、醫療院所

### M1 出院摘要改寫為轉診信

**情境**：醫師把一份出院摘要（Word）交給 Arlo，請它改寫成給區域醫院的轉診信，語氣正式、重點列出診斷、用藥與追蹤建議。

- **輸入**：出院摘要 docx，內容含病患姓名、病歷號、出生日期、身分證字號、診斷、用藥、主治醫師。
- **偵測與政策**：
  - `person` ×2（病患、醫師）→ alias；
  - `gov_id` ×1 → confirm；
  - 出生日期 → 最小化，泛化為年齡；
  - 病歷號（自訂詞彙規則）→ alias；
  - `health`（診斷、用藥）→ confirm。
- **Route**：R1。文件是非結構化短文字，不算 `dataset`。
- **流程**：

```
醫師 ─► Privacy Agent
          │ Detect：人名、身分證、病歷號、出生日期、診斷、用藥
          │ 最小化：轉診信不需要身分證 → 移除；出生日期 → 「58 歲」
          │ confirm 類別（health）→ R4
          ▼
     ┌───────────────────────────────────────────────┐
     │ 隱私確認：即將送出的內容                         │
     │ 「⟦PERSON_1⟧，58 歲男性，病歷號 ⟦ID_1⟧，        │
     │   診斷：第二型糖尿病併周邊神經病變…              │
     │   主治：⟦PERSON_2⟧」→ 目的地：OpenAI（雲端）      │
     │ [允許送出] [改為只在本機處理] [取消]            │
     └───────────────────────────────────────────────┘
          │ 允許
          ▼
     Planner / Operator（雲端）撰寫轉診信（只看到別名）
          │ Gate 回應驗證：⟦PERSON_1⟧、⟦ID_1⟧、⟦PERSON_2⟧ 完整
          ▼
     Privacy Agent 還原真值 → 轉診信 docx 存到 workdir → 隱私卡片 + Ledger
```

- **雲端看到什麼**：別名化的姓名與病歷號、年齡、診斷與用藥文字；看不到身分證與出生日期。
- **使用者確認點**：1 次（health 類別第一次外送）。
- **嚴格**：`health` 為 block，診斷會變成 `⟦REDACTED:health⟧`，雲端寫不出有意義的轉診信。SLM Flow 會改建議 R3，由本地模型撰寫。
- **SLM／LLM**：SLM 模式由程式依政策先走 R4 再交給 Planner；LLM 模式由 Privacy Agent 自己呼叫 `delegate_minimized(keep=[診斷, 用藥])`，也可以判斷本地模型足以勝任而直接 R3。

### M2 門診月報統計

**情境**：醫務室每月從 HIS 匯出門診紀錄 CSV（約 3 萬列），要統計：各科門診量、前 10 大 ICD-10 診斷、年齡層分布、回診率，並產生圖表。

- **輸入**：`opd_2026_08.csv`，欄位：`chart_no, name, id_no, birth_date, visit_date, dept, icd10, doctor, fee`。
- **偵測與政策**：`dataset` → schema_only；欄位名 `name`、`id_no` 本身不敏感，但其值屬 `person`／`gov_id`。
- **Route**：R2 compute-to-data。
- **流程**：

```
Privacy 端（本機）                                   雲端 Operator「資料整理員」
───────────────────────────────                     ───────────────────────────
opd_2026_08.csv
 │ 確定性解析器
 ▼
DatasetDescriptor
  file: ⟦FILE_1⟧, rows: 10k–100k
  chart_no: string /[0-9]{8}/
  name: string (person)       ← 只有型別與類別
  id_no: string /[A-Z][12][0-9]{8}/ (gov_id)
  birth_date: date, visit_date: date
  dept: enum(12)  icd10: string /[A-Z][0-9]{2}(\.[0-9]+)?/
  fee: int
  合成樣本 5 列（假值）                ──(Gate)──►  撰寫 pandas 腳本
                                                     groupby dept / icd10、
                                                     年齡層、回診率、matplotlib
                           ◄── submit_compute_script(python, …) ──
 │ 靜態檢查（import 白名單：pandas、numpy、matplotlib）
 ▼
沙箱執行（無網路、in/ 唯讀、只寫 out/，120s / 2GB）
 │ out/summary.json、out/*.png
 ▼
預設：Privacy Agent 組月報給使用者（真實數字不出本機）
```

- **雲端看到什麼**：欄位結構、格式樣式、列數級距與假樣本；沒有任何真實病患資料或統計數字。
- **使用者確認點**：0 次。
- **延伸**：使用者要求「依統計結果寫一段給院長的分析文字」時，需要 Operator 繼續推理。`out/summary.json` 經 Gate 回給 Operator，並套用：
  - 列數上限 50；
  - 小格抑制：例如某罕見 ICD-10 在某科只有 3 人，計數改為 `<5`，避免以小樣本回推個人。
- **失敗重試**：腳本因日期格式錯誤失敗時，traceback 可能含真實值（例如 `ValueError: '1968/0x/12'`），會先經 Gate 再回給 Operator。

### M3 健保申報核對

**情境**：申報人員比對「院內申報明細 XLSX」與「健保署核減通知 CSV」，找出核減項目與原因並產出待補件清單。

- **Route**：R2（兩個資料集，腳本以 `chart_no` 與日期 join）。
- **重點**：
  - 腳本輸出 `out/to_resubmit.xlsx`，寫到 workdir 的新檔案，自動完成。
  - 若使用者要求「直接更新原本的申報明細檔」，屬寫回使用者原始檔案，為 `high` 風險，強制人工確認（ADR-0017 第 9 點）。
  - 待補件清單含姓名與病歷號，屬於列層級資料，超過列數上限時只給使用者，不回 Operator。

### M4 臨床問題文獻查證

**情境**：醫師問「一位 72 歲、eGFR 28、正在服用 apixaban 的病人，合併使用 clarithromycin 的交互作用與劑量建議？」並附上該病人的用藥清單截圖。

- **偵測與政策**：
  - 截圖 OCR 到病患姓名與病歷號 → alias 並塗黑；
  - 年齡、eGFR、藥名屬 `health` → confirm。
- **Route**：
  - SLM 模式：最小化後問題本身不含可識別資訊（只剩年齡、腎功能、藥名），但仍屬 `health`，依政策先 R4 確認，再 R1 交 Planner → Operator「醫學文獻研究員」。
  - Operator 以瀏覽器查 PubMed、仿單等公開來源（`public` → allow）。
- **雲端看到什麼**：「72 歲、eGFR 28、apixaban + clarithromycin」，以及塗黑姓名、病歷號的截圖。
- **注意**：這是 prompt injection 風險最高的情境之一，Operator 會讀大量外部網頁。但 Operator 手上只有別名，網頁若誘導它把 `⟦PERSON_1⟧` 送到其他網站，還原時會觸發新網域確認（ADR-0015 第 17 點）。

### M5 預約與掛號系統操作（Phase 2，computer use）

**情境**：櫃台請 Arlo 依一份「複診名單」逐一在院內掛號系統（桌面 App）建立預約。

- **設定**：Operator「櫃台助理」的 `computerUse.apps` 只包含掛號系統；截圖中其他視窗（例如 LINE、信箱）塗黑。
- **流程**：

```
複診名單（XLSX，含姓名、病歷號、電話、希望時段）
 │ 名單屬 dataset，但任務是逐筆操作 UI 而不是計算，R2 不適用
 │ → 使用者在確認卡片改走 R1（LLM Flow 可自行選擇）；每筆以別名交給 Operator
 ▼
Operator（雲端）看到：「為 ⟦PERSON_3⟧（病歷號 ⟦ID_3⟧）預約 9/30 上午 心臟內科」
 │ computer_screenshot → Gate：OCR 塗黑畫面中的姓名、電話，標註別名
 │ computer_type("⟦ID_3⟧") → 工具邊界還原為真實病歷號 → 輸入本機 App
 │  （本機白名單 App，不是網路外送 → 不需確認）
 ▼
完成後回報，Privacy Agent 還原別名產出「已預約清單」
```

- **使用者確認點**：`health` 類別 confirm 一次（名單含科別）；`computer_*` 為 medium，派發者可代批；使用者一動滑鼠即暫停。
- **限制**：OCR 漏抓的內容（例如手寫體掃描）仍可能送上雲，這是 ADR-0018 列出的已知風險。

### M6 衛教與病患通知信

**情境**：依檢驗結果寄發個人化衛教信給 40 位病患。

- **Route**：
  - R2 由腳本把檢驗結果分成 5 種衛教模板類別，只輸出「類別 → 病患別名清單」；
  - R1 請雲端撰寫 5 份模板（不含任何個人資料）；
  - 本機合併模板與真實姓名。
- **寄信**：屬 `high` 風險（送出訊息／郵件），每批次強制人工確認（ADR-0010）。
- **Outbound 通知**：若設定 Telegram 轉發「任務完成」，通知內容中的姓名會被 `⟦REDACTED⟧` 取代（ADR-0012 第 17 點）。

## 二、法律事務所

### L1 合約審閱（NDA／租賃契約）

**情境**：律師上傳客戶的租賃契約 PDF，請 Arlo 標出對承租人不利的條款、提出修改建議，並比較市場常見條款。

- **偵測與政策**：
  - 當事人姓名、公司名 → `person`／alias；
  - 統一編號、地址 → alias；
  - 租金與押金金額 → 預設不視為敏感，但可用自訂詞彙規則設為 `org_confidential`；
  - 案件代號（自訂詞彙）→ `org_confidential` → confirm。
- **Route**：R1。
- **雲端看到什麼**：

```
「本契約由 ⟦ORG_1⟧（出租人，統一編號 ⟦ID_1⟧）與 ⟦PERSON_1⟧（承租人）
  就 ⟦ADDRESS_1⟧ 之房屋訂立…第 12 條：承租人提前終止應賠償 ⟦AMOUNT_1⟧…」
```

- **產出**：修改建議以別名回傳，Privacy Agent 還原後產出附註解的 docx。
- **為什麼可行**：條款審閱靠的是條文結構與法律語意，別名不影響判斷。金額被別名化時，雲端無法判斷「違約金是否過高」，這時 LLM Flow 可選擇 `keep=[AMOUNT_1]`，SLM 模式則會在確認卡片上讓律師決定是否保留金額。

### L2 訴訟案卷時間軸整理

**情境**：一件勞資爭議的案卷，含 200 封電子郵件匯出（EML）、LINE 對話紀錄匯出、會議紀錄。律師要一份依時間排序的事實時間軸，並標註每個事件的證據出處。

- **偵測與政策**：大量人名、email、電話、公司內部代號；內容以非結構化文字為主，但總量大（超過 200 列門檻）→ 判定為 `dataset`。
- **Route 選擇**（此情境兩種 route 都合理）：
  - **R2**：腳本只能做結構化抽取（寄件者、日期、主旨），寫不出「事實敘述」，不適合作為主要路徑。
  - **R1 分批**：每封郵件別名化後交給 Operator 摘要成事件。同一案卷在同一個 privacy scope，所以「⟦PERSON_4⟧」在 200 封信中都指同一人，時間軸前後一致（ADR-0015 第 18 點）。
  - SLM Flow 依規則會先走 R2。使用者可在確認卡片選擇改走 R1；LLM Flow 可自行組合：先 R2 抽出日期與寄件者索引，再 R1 逐批摘要。
- **雲端看到什麼**：別名化的郵件內文；雲端能理解「⟦PERSON_4⟧ 於 3/12 要求 ⟦PERSON_1⟧ 加班」，但不知道真實身分。
- **跨任務**：下週另開 Thread 追加新證據時是新的 scope，別名重新編號。若要延續同一套別名，必須在同一條 Thread 內繼續。

### L3 工時與帳單統計

**情境**：事務所匯出一季的工時紀錄（SQLite），統計各案件、各律師的可請款時數、實收率、逾期帳款，並產出給合夥人的報表。

- **Route**：R2。
- **雲端看到什麼**：資料表結構與假樣本（`matter_id`、`client_name`、`lawyer`、`hours`、`rate`、`billed`、`paid_date`）。
- **小格抑制**：按客戶分組時，只有 1–2 筆的客戶不會以原數字回給 Operator。
- **結果**：預設只給使用者；合夥人報表的文字說明若要雲端撰寫，只提供彙總表（經 Gate）。

### L4 判決與法規檢索

**情境**：律師問「雇主以『業務緊縮』為由資遣，但同時新聘同職缺人員，最高法院近五年見解為何？」

- **偵測**：問題本身沒有個資 → R0 直通。
- **Operator**：「法律研究員」以瀏覽器查司法院法學資料檢索系統、全國法規資料庫（`public`）。
- **若問題附帶案情**（「我的當事人王大明在 XX 公司任職 8 年⋯」）：R1 別名化後再檢索，檢索關鍵字不會含真實姓名。

### L5 起訴狀草擬與電子書狀遞送

**情境**：依 L2 的時間軸草擬起訴狀，完成後由 Operator 在法院電子訴訟系統填寫書狀資料並上傳。

- **草擬**：R1，在與 L2 同一條 Thread 內沿用別名。
- **填表遞送**：Operator 以瀏覽器操作電子訴訟網站。
  - `browser_type(ref, "⟦PERSON_1⟧")` 在工具邊界還原為當事人真實姓名。
  - 電子訴訟網站的網域不在本 Task 的網域集合中（使用者沒提過、也沒導航過），第一次還原真值送往該網域時觸發 `privacy_confirm`（`new_domain_egress`）。律師核准後，該網域加入集合，同一任務後續欄位不再詢問。

```
browser_navigate("https://<電子訴訟系統>") ─► 網域加入集合？
   │  否：導航本身不含還原值 → 允許，並把網域加入集合
   ▼
browser_type(姓名欄, "⟦PERSON_1⟧")
   │ 還原 → 真實姓名；目的網域已在集合中 → 執行
   ▼
上傳書狀、送出 ─► 送出書狀屬 high 風險 → 強制律師確認
```

- **auth_required**：電子訴訟需要自然人憑證或律師憑證登入，一律由律師在 Operator 視窗的瀏覽器親自完成（ADR-0010）。

> 導航本身會把網域加入集合，因此 prompt injection 若先誘導 Operator 導航到惡意網域，再輸入真值，就不會觸發確認。這是 ADR-0015 第 17 點「已導航過的網域」規則的漏洞，列於本文件末的「設計缺口」。

### L6 利益衝突檢查

**情境**：新案件委任前，比對對造與關係人名單是否出現在事務所既有客戶與對造資料庫（SQLite，約 5 萬筆）。

- **Route**：R2。
- **特殊處：要比對的名字本身就是敏感資料**。腳本需要以「新案件的關係人姓名」為參數，在本機做精確比對與模糊比對（同音字、公司簡稱）。
  - 雲端 Operator 只拿到 `⟦PERSON_7⟧`、`⟦ORG_3⟧` 這類別名與資料庫 schema，寫出比對邏輯。
  - 腳本參數中的別名要在本機沙箱執行前還原為真值。**這一點 ADR-0017 尚未定義**（目前 `inputs` 只接受資料集別名），列入設計缺口。
- **結果**：命中清單只給律師，不回雲端。這類結果本質上就是列層級個資。

### L7 掃描證據與截圖整理

**情境**：當事人提供 50 張手機截圖（對話、轉帳紀錄）與掃描的紙本合約，請 Arlo 整理成證據清單（編號、日期、內容摘要、證明事項）。

- **流程**：
  - 圖片進入模型前，由 Gate 做本地 OCR → 偵測 → 塗黑姓名、帳號、電話並標註別名（ADR-0015 第 20 點）。
  - `financial_account`（轉帳帳號）→ confirm。
  - 雲端 Operator 看到的是塗黑後的截圖與 OCR 別名文字，依此撰寫摘要。
- **限制**：手寫、低解析度或特殊字型的截圖，OCR 可能漏抓。建議這類案件改用「嚴格」等級，或改在 LLM 模式以本地自架大模型處理（R3）。

## 五、從情境中發現的設計缺口

以下問題在套用情境時浮現，現有 ADR 尚未定義，建議另行盤問後補入：

1. **腳本參數的別名還原**（L6）：`submit_compute_script` 目前只接受資料集別名作為 `inputs`。比對、篩選類腳本需要以敏感值為參數，需定義「參數中的別名在沙箱執行前於本機還原」，以及還原後的值不得出現在回給 Operator 的輸出中。
2. **導航即加入網域集合的漏洞**（L5、M4）：ADR-0015 第 17 點把「Operator 已導航過的網域」列入 Task 網域集合，prompt injection 可以先導航到惡意網域，再輸入真值而不觸發確認。建議改為只有使用者提過、或使用者核准過的網域才算數，或者網域必須在還原前就已被使用者確認。
3. **大量非結構化文字的 route**（L2）：`dataset` 規則以列數判定，會把 200 封郵件導向 R2，但這類任務實際需要 R1 分批。需定義「非結構化大量文字」的判定與分批策略，以及分批時的 Gate 成本。
4. **跨 Thread 延續同一案件的別名**（L2、L5）：scope 以 Thread 為單位，同一案件分多次處理時別名會重新編號。可考慮「案件 scope」，讓使用者把多條 Thread 綁定為同一案件，但會提高跨任務可連結性，需權衡。
5. **產業預設包**（第四節）：醫療與法律的自訂詞彙、類別覆寫、Operator 範本可以做成可匯入的「機構設定包」，目前 ADR-0016 只有個人層級的覆寫。
6. **小格抑制的適用範圍**（M2、L3）：目前只在 `outputSpec` 宣告為彙總表時生效，Operator 可以不宣告。應考慮對所有回給 Operator 的表格自動偵測計數欄位。
